## Honest limitation

This sandbox has no network access, so a real Postgres/Supabase instance
could not be installed here to actually run these migrations. What I did
instead, since "the SQL parses in my head" isn't good enough for a
schema:

- **Every migration file** was checked for balanced parentheses and
  quotes with comments correctly stripped out first (a naive check
  mistook English contractions like "it's" inside SQL comments for
  unbalanced string literals on the first pass — fixed before trusting
  the result).
- **Every foreign key** was verified programmatically to reference a
  table and column that actually exists, and that the referenced table
  is created in an *earlier* migration file (not a forward reference,
  which Postgres would reject).
- **The `inquiries` table's 24 columns** were compared, as an exact set,
  against the field list you gave — confirmed identical, nothing missing
  or added.
- **The `inquiry_status` enum's 7 values** were compared the same way —
  exact match.
- **Every one of the 12 tables** (10 requested + 2 join tables, see
  below) was confirmed to have Row Level Security enabled, and every
  RLS-enabled table was confirmed to have at least one policy (RLS
  enabled with zero policies silently denies all access, which is easy
  to do by accident and easy to miss in review).
- **The seed data** (see below) was generated by a script that actually
  imports the real frontend data files and was actually executed — not
  hand-written — and its output was checked column-by-column against the
  schema.

None of this substitutes for actually running `supabase db push` (or
equivalent) against a real project and confirming it applies cleanly —
that's the one step only you can do from here, and I'd treat it as the
real test.

## Two tables beyond the requested 10

`industry_categories` and `industry_capabilities` — join tables
normalizing the `categories: [...]` and `capabilities: [...]` arrays
already present in `frontend/src/data/industries.data.js`. Both sides of
each relationship are real, independently-managed entities referenced
from multiple places, which is exactly the situation a many-to-many join
table exists for (as opposed to, say, a product's `applications` list,
which stays a plain array because it isn't a shared entity). Documented
here rather than added silently.

## Applying the migrations

**Option A — Supabase CLI** (recommended if you're using Supabase):
```bash
supabase link --project-ref <your-project-ref>
# copy or symlink database/migrations/* into supabase/migrations/ first,
# since the CLI expects that exact folder name
supabase db push
```

**Option B — plain psql** (works against any Postgres, Supabase or not):
```bash
for f in database/migrations/*.sql; do
  psql "$DATABASE_URL" -f "$f"
done
```

Migrations are numbered `20260101000001` through `20260101000013` — the
dates are placeholders marking creation order, not real historical
dates. Renumber with real timestamps if you're adding these to an
existing Supabase CLI migration history.

## Seeding real content

The seed file isn't hand-written — it's generated directly from the same
data files the live site already renders from
(`frontend/src/data/{categories,capabilities,industries,products,blogPosts}.data.js`),
so it can never drift out of sync with what the site actually shows.
Regenerate it any time those files change:

```bash
node database/scripts/generate-seed.mjs
```

Then load it the same way as the migrations:
```bash
psql "$DATABASE_URL" -f database/seed/001_content_seed.sql
```

**Update**: `blog_posts` now has real seed data too — 10 real articles
generated from `frontend/src/data/blogPosts.data.js`, the same content
`/blog` renders from. `contact_messages` and `inquiries` still have none
— seeding fake customer inquiries would misrepresent that any real
customer submitted them, which is a different situation from blog
content that was legitimately written as real site copy.

A real bug was caught and fixed while adding the blog_posts generation:
the code that builds those INSERT statements was initially placed
*after* `generate-seed.mjs` had already written the output file to disk,
which would have made the blog data silently never appear in the actual
seed file despite the script reporting success. Caught by running the
generator and grepping the real output for `insert into blog_posts`
statements, not by reviewing the code change alone.

## Row Level Security — the design in short

- **Marketing content** (categories, products, images, industries,
  capabilities, the two join tables, company settings): publicly
  readable by anyone, not publicly writable by anyone. All content
  management happens through the backend's Supabase **service role**
  key, which bypasses RLS by design — there are deliberately no
  INSERT/UPDATE/DELETE policies for the `anon`/`authenticated` roles on
  these tables.
- **`blog_posts`** is the one exception with a filtered read policy —
  public visitors can only see rows where `published = true`; drafts
  stay invisible until the service role publishes them.
- **Customer-submitted data** (`inquiries`, `inquiry_files`,
  `contact_messages`): the reverse — publicly *insertable* (anyone can
  submit an RFQ or contact form), but **not publicly readable at all**.
  No SELECT policy exists for `anon`/`authenticated` on any of these
  three tables. That's intentional, not a gap — read `migrations/
  20260101000013_row_level_security.sql`'s header comment for the full
  reasoning, including the honest tradeoff that public INSERT with no
  ownership check means nothing at the database level rate-limits
  submissions (that belongs at the application layer).

## Known gap — now resolved

Previously documented here as unresolved: `inquiries.product_id` is a
UUID foreign key, but the live `/quote` wizard captures a free-text
product name and only sometimes a slug string. Resolved in
`backend/src/services/inquiry.service.js`'s `resolveProductId()` —
looks the frontend's slug up against `products.slug` and uses the real
UUID, or `null` for free-text/custom requests that don't match anything
in the catalogue. The free-text product **name** itself is still stored
nowhere in this table (only `inquiries.message` and the resolved FK) —
if capturing the exact text a visitor typed matters later, that's still
a real follow-up migration (a `product_name_text` column), just no
longer the blocking gap it was.
